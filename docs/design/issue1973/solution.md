# #1973 发送尝试始终可见：方案与用户旅程

范围：方案、UI 设计、可操作演示及渲染证据。用户原始要求与 Issue #1973、维护者 2026-11-12 的回复为本轮依据；不将演示稿当作产品修复或真实 Agent 验收。

## 设计决定

沿用现有聊天页与本人气泡，只在原气泡下显示一行状态及必要恢复动作。点击发送，就出现正文/附件完整的本人气泡。发送是否受理、是否交给成员、是否已读分别由相应证据推进，同一气泡原位更新。输入框清空不能早于发送内容已有可恢复副本。

第一现场是这条消息；不另建发送中心、状态仪表盘或抢占页面的大错误卡。

```yaml
in_context_observability:
  primary_surface: 本人消息气泡及其紧邻状态行
  why_not_dashboard_only: 用户需要在刚刚发送的原处确认内容仍在、现在该等还是该操作
  deep_dive_surface: 沿用原有消息详情与诊断入口，按需展开
  noise_dedup_policy: 同一发送尝试只保留一条气泡；状态替换而非追加系统消息
```

## 状态与界面文案

| 事实 | 气泡下的呈现 | 用户操作 |
|---|---|---|
| 点击发送，尚未得到受理回执 | 中性旋转图标 +「发送中…」 | 等待；可以继续写下一条 |
| 已受理，确实在等待忙碌成员 | 中性时钟 +「排队中 · 等砚砚接收」 | 不必再发；不杜撰队列数量 |
| 已受理且立即执行 | 仍为中性「发送中…」，随后按交付事实推进 | 不强制停留在排队动画 |
| 权威交付确认 | 现有头像/姓名回执 +「砚砚已收到 · 等读取确认」 | 原气泡不新增副本 |
| 确认已读且对应回复正在进行 | 沿用现有「已读 / 正在回复」回执 | 可以打开精确关联的回复 |
| 明确未受理 | 红色感叹号 +「未发出」+ 简短原因 |「重试」；保留正文、附件和同次发送身份 |
| 已受理，但某目标明确投递失败 | 对该成员显示红色「没送到」 | 沿用「重新发送」；为该目标创建新投递，保留失败记录，不重放已成功目标 |
| 超时/断线，尚不知是否受理 | 琥珀色问号 +「暂未确认是否发出」 |「检查状态」；不把未知当失败，不自动换编号重发 |
| 核查进行中 | 中性旋转图标 +「正在确认…」 | 暂停重复点击；内容保持可见 |

状态必须同时有文字和图标，不只靠颜色。失败只强调状态与恢复动作，正文保持正常对比度。已收到不等于已读；成员已回复也不能替代精确读取证据。多目标沿用同一条本人气泡下的逐成员回执。

## 三条主要旅程

### A. 正常发送 / 成员忙碌

1. 用户写好正文并附图，按发送。
2. 当次用户操作的下一次绘制就出现本人气泡，显示「发送中…」；不能等待 HTTP、Socket 或 Agent。
3. 服务端确认入队。成员忙碌时原位变为「排队中 · 等砚砚接收」；成员空闲时不故意插入排队停顿。
4. 交付确认到达，原气泡变为现有成员回执；已读状态在得到读取证据后单独更新。
5. 用户继续输入，前一条状态更新不移动其阅读位置、不抢输入焦点。

### B. 明确失败 / 原位重试

1. 点击发送即有气泡，随后收到明确拒绝受理。
2. 同一气泡保留原文和附件；下方红色感叹号、原因、「重试」。
3. 点击一次重试，该操作临时不可重复，原气泡变为发送中；不用把内容复制回输入框，不制造第二条本人气泡。
4. 同一次发送的传输重试复用稳定身份。若是已交付之后的成员投递失败，则按现有契约为失败目标新开一次投递；两者不能混用。

### C. 断线 / 结果未知 / 切换或刷新后恢复

1. 请求已发出但确认丢失，原气泡变为「暂未确认是否发出 · 检查状态」。
2. 用户切换会话、返回或刷新，仍能看到原来的正文、附件与待确认状态；不丢进输入框，也不消失。
3. 点击检查，或连接恢复后自动核查同次发送的权威回执。
4. 查到已受理：与服务端原消息对账为同一气泡；查到明确失败：进入失败恢复；暂时查不到：仍是未知，不能凭一个空队列或一次未找到就断言没发送。
5. 确需继续原发送时，复用原身份；若用户明确选择「再发一次」，沿用现有重复风险提示并使用新身份。这是新的用户决定，不是系统暗中重发。

## 实现建议：一个发送尝试记录、一个可见投影

建议增加浏览器端持久发送尝试 Outbox，复用现有 POST 幂等能力和 Queue/History。它只描述用户这次发送，不创建 invocation，也不伪造服务端 History。

- 发送时固定 `clientMessageId`、账号、原 thread、正文、附件 Blob/引用、回复引用与目标意图。同步进入可见投影，异步持久化到 IndexedDB；本地快照提交后再清空输入框并发起网络发送。本地存储失败时保留输入框和原气泡，明确告知没有继续发出。
- 未完成尝试与附件默认无过期时间。恢复始终按账号和 thread 隔离；回到会话时先恢复本地未完成尝试，再做网络核查。
- 现有 `POST /api/messages` 的 `idempotencyKey` 复用这个稳定身份。受理回执后记录 `serverMessageId`，与 Socket、Queue、History 使用同一身份映射。
- 必须覆盖 Socket 早于 HTTP 的顺序：当前入队路径先发 `queue_updated`、后回 202。不能假定 202 之前 Queue 没有消息；若回执现有字段不足以关联本地尝试，应在授权范围内补充稳定关联键，而不是通过正文相同来猜测去重。
- 展示层合并本地尝试、已确认 Queue 投影和 History，同次发送只取一份内容及最可靠的状态。Queue 条目消失不能单独删除气泡；必须已有同身份的权威消息接替，或已知失败由原气泡解释。
- 目前服务端内部已有 `getByIdempotencyKey(userId, threadId, key)`；浏览器不能把普通 History 或空 Queue 当作按键查询。若无现成入口，设计一条账号/thread 授权的只读受理回执查询；未找到表示暂未查到，不能自动宣称拒收。
- HTTP 较晚返回时不能覆盖已经到达的交付/读取事实；跨会话结果只写原 thread。明确失败与未知由真实证据区分，不用单纯计时把未知变成失败。

生产代码落点建议：`useSendMessage` 负责创建/提交尝试，`ChatInput` 调整清空时点；独立的持久尝试 owner 管恢复，`useChatHistory`/`queued-input-preview` 接同一可见合并；`useSocket` 仍处理权威事实。复用现有 `MessageDispatchAvatars`、错误与重试动作，不新增平行的成员执行账本。

本地发送未受理时的 pending 记录只用于界面和恢复，不作为模型上下文。服务端最终接纳后按原消息身份收敛；失败尝试不能假冒已落库内容。

## 视觉约束与验收

- 继承 DESIGN.md 的暖纸、发丝线和 4px 节奏，沿现有右对齐本人气泡；状态行在时间和回执附近，正常中性，失败红色，未知琥珀。
- 本文案与现有「谁收到了」回执一致，不用只有头像没有文字的微型标记。
- 气泡进入仅轻微位移/显现；状态原位切换不移动正文。发送/重试控件有按下与键盘焦点反馈；减少动态时保留等效静态图标和文字。
- 验证 1440px 桌面、390px 窄屏、长正文/附件、键盘操作及真实 200% 缩放；失败与未知不截断关键动作。
- 产品验收必须从真实发送入口覆盖：请求未返回、已受理但无 Socket、拒绝受理、结果未知后服务端已保存、成员忙碌、切换/刷新、HTTP 迟到、单次尝试不重复入队。设计演示只能证明交互意图与布局，不能代替这些真实服务端验收。

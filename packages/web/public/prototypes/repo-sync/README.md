# 单向交付接收：交互原型

依据：上游 Issue #1582 的 v2 讨论；指定上游版本初始化，内部只接受外部交付，核心文件树一致，允许初始化与接收合并提交，两侧 main SHA 不必相同。

- demo_kind: journey_validation
- delivery_lane: internal_product_gate
- 主判断：用户能否直接辨认是否最新、版本对应关系、未合入 PR 与当前卡点，并在等待／失败后继续同一笔交付。
- 本轮体验判断：用户无需先理解全部同步机制，就能在首屏判断现在由谁处理、点击哪里、点击后会发生什么。每个实际状态只有一个主操作；技术对照按需展开。配置分为地址、基线、检查与初始化三步，演示控制默认收起。
- visual_source_of_truth: packages/web/src/app/theme-tokens.css、console-tokens.css；components/settings/SettingsShellV2.tsx 的 232px 导航、工作面及细分隔线。
- native_elements: 直接加载当前 worktree 的原生主题 token，沿用设置功能页的导航／工作面结构。
- surface: 单功能原型；独立预览，不声称已挂载真实应用 Host，也不替代产品主壳。
- stylized_elements: 仅流程图、版本桥和演示控制；演示控制可以隐藏。
- truth_label: 全部仓库、SHA、Issue、PR、命令结果都是合成数据；实际 Git、平台 CLI、网络及后端未接入。

当前界面分层：当前状态与唯一主操作 → 五段进度及其具体子步骤 → 轻量版本对照 → 按需展开的命令说明 → 同步记录。导航只保留“同步工作台”和“仓库设置”；映射、检查、命令和审计从具体同步进入。审计属于交付与 PR，没有独立导航 tab。是否最新比较 acceptedUpstream 与 latestUpstream，不比较内部 main SHA；代码最新但元数据未补齐仍显示未完成。

2026-10-12 交互修订：内部候选分支为 `sync/{deliveryId}`，目标分支使用绑定配置；内部 PR 标题为 `[上游同步] PR #{sourcePr} · {title}`。同一交付重试复用分支与 PR。配置页展示规则与预览，总览流程和 PR 页展示本次实际命名。命名规则为原型默认值，不暗示真实平台对象已创建。

落地时要求交付 ID 在同一内部仓唯一，冻结后不因重试或上游新增交付而改名；演示编号仅为示例。标题中的 PR 号是外部来源号，内部 PR 编号仍由内部平台创建时生成。

“合入后核验”和“确认关单结果”保留独立场景起点，模拟结果入口位于首屏当前任务卡，与人工审核入口共用同一位置。隐藏顶部控制条后仍可操作；只浏览技术节点不改变实际状态，也不能越过审批。映射页仅展示 commit / Issue / PR 对应，审计和检查在本次同步详情按需展开。

首次使用展示“开始配置仓库”，配置分为连接地址、内外同步基线、检查与启用三步。演示地址与两侧版本已实际预填，可不输入任何内容直接完成配置；“填入示例仓库”可恢复被清空的地址。可选网页地址与 CLI 默认折叠。已有连接提供只读摘要，未完成同步时禁止进入修改。没有已保存状态的浏览器从未配置开始；显式“演示场景”控件可载入预设模拟状态，正常同步入口仍不能跳过基线登记。

操作与结果：未配置 → 开始配置；待接收 → 同步明确的上游 PR；系统准备 → 继续演示当前准备步骤；待审批 → 跳到明确的内部 PR；核验 / 核对中 → 演示当前自动环节；阻塞 → 明确查询 / 重跑 / 查看处理方法；已最新 → 回看最近记录。历史同步只提供返回当前工作台，不能推进别的 PR。

审计按 deliveryId 筛选，记录步骤、执行方、内外对象、结果和审批备注；新发现的交付日志归新交付，不归活动 PR。预置场景记录明确标注“演示预置”，旧版缺少来源身份的发现记录保留原数据并标注归属待核对，不补造关联。新记录使用北京时间的完整日期与时间。

仓库连接扩展：导航提供“仓库设置”。配置外部 GitHub / 内部 Git 地址、来源 / 目标分支、可选内部网页地址、Issue / PR 平台 CLI。第二步默认“已有内部仓：继续同步”，明确登记外部上次已同步 commit A 与内部当前 commit B。新仓初始化另选独立快照或保留历史，两种模式都标注仅适用于空内部仓。无绑定或未启用时禁止同步。检查执行输入格式校验与模拟基线结果，不声称已验证真实访问权限或 Git 对象。

配置旅程：使用示例或修改地址 → 确认 A/B → 检查配置与基线（模拟）→ 保存新绑定 → 登记已有基线并启用 → 同步下一笔。有未完成交付时禁止更换绑定；已有绑定替换时归档旧合成映射与记录。修改输入使检查结果失效。已有仓接管保留输入的 B，不生成新的内部 commit；新仓才演示建立初始 commit。演示无需认证，不提供 Token / 密码或认证配置名称输入；仍拒绝地址中的凭据与查询参数。

2026-10-12 演示入口修复：此前真实地址形式的占位提示掩盖了空输入，导致点击下一步报错；认证引用没有对应的管理能力却参与必填校验。现已移除这两项阻塞。样例只预填 UI 草稿，不提前保存或初始化；已有自定义地址与待初始化绑定保持原值。旧状态中的认证名称不再显示或校验，新绑定也不保存这些字段。正式接入认证的界面与运行时尚未实现。

## 已有内外仓、内部落后 20 个提交

外部上次同步到 A，内部当前停在 B。若原样保留历史，B 可以就是 A；若经过独立初始化或接收合并，ID 可以不同，但核心代码需一致。第二步填 A/B，第三步展示对应与核验项目；A 是已经同步完成的版本，不填外部最新版本。示例接管后展示 20 个提交、4 个已合入 PR，逐笔创建内部候选与 PR。每笔合入后核验通过才推进 acceptedUpstream；Issue 核对完成后开放下一笔。配置摘要同时显示初始 A/B 和当前已接受外部 / 内部版本，接管基线不需要每次重填。

正式实现应按以下契约接管：

1. 读取远端与完整历史，解析两侧完整 SHA；确认 A 是指定外部分支历史上的提交、B 是内部目标分支当前 HEAD。发现现存未完成同步 PR 时先恢复该笔记录。
2. 在同一个本地对象库获取两侧对象，以 `git diff --exit-code A B -- .` 比较核心仓全部受跟踪内容。无需 A/B commit SHA 相同；核心仓中不容纳定制插件差异。差异不为空时暂停，输出差异列表，由用户修复或选择正确已同步版本。
3. 登记 `acceptedUpstream=A / internalHead=B` 及仓库、分支、核验结果。启用前与开始同步前重新读取内部 HEAD，拒绝过期 B。接管本身只登记；候选和 PR 在后续接收阶段创建。
4. 待接收范围由外部 `A..upstream/main` 计算，例如 `git rev-list --count A..upstream/main`。按已落地 PR 形成有序交付；20 个提交不等于 20 个 PR。不能用内部 B 直接计算外部增量；没有关联 PR 的提交也需作为明确交付登记，不能遗漏。基线处于某个 PR 中途时需显式处理部分交付，不把整个 PR 误认作未接收。
5. 每笔核验后记录 `目标上游 U ↔ 实际内部合入 I` 并推进接受游标；历史 A 及更早版本不重新搬运、建 Issue 或建 PR。历史对象映射如需导入，应单独核对，不凭 A/B 自动推断。两个仓库源历史尚未连接时，先判断祖先关系；只在已确认同树的首次候选分支连接历史，再经内部 PR 合入。

上面是待落地的真实 Git / 平台执行契约。当前 `baseline.mjs` 只提供明确标记的模拟核验，可切换“核心树不一致 / 内部 HEAD 已前进”证明阻断路径；模拟通过不会证明输入 SHA 在真实仓存在。原型接管后的 20 个提交是预置数据，不是访问用户仓库得到的数量。依据：[Git diff](https://git-scm.com/docs/git-diff)、[Git merge-base](https://git-scm.com/docs/git-merge-base)、[Git rev-list](https://git-scm.com/docs/git-rev-list)。

原型使用 localStorage 保存合成操作、审批备注及场景；不保存凭据。重置仅覆盖此原型合成状态，不连接生产数据。

职责：人工只在内部平台按正常流程审核／合入 PR。准备、比对、映射、模板文档、检查、结果读取与完成登记由程序执行，不依赖 Agent。Agent 可选辅助生成可读变更说明或解释失败，不能替代版本核验、关闭依据和审批。当前没有接入模型。

九步命令说明保留在折叠详情中；用户进度为准备同步、审核 PR、核验代码、确认关单结果、完成，每个大步骤直接展示子步骤。准备包含校验并冻结目标、创建 / 复用内部 Issue、搬运提交与候选分支、创建 / 复用内部 PR、运行代码与插件检查。标记为 ✓ 完成、● 当前、○ 待执行、× 异常，替换主描述的“1/5”。子步骤从同一 phase / block 推导，读取合入结果在进入核验时已完成，读取 Issue 状态在进入关单确认时已完成；没有增加独立进度游标。异常大步骤、具体子步骤和同步记录均显示 ×，页面展示错误码、原因与处理方法；错误信息作为文本转义。当前错误均来自演示场景，尚未接入真实执行器日志。

## Issue 搬运与关单结果

新增共享 Issue 场景：U1/U2 两笔共用外部 #71 → 内部 #318。U1 保存本笔接收记录后 COMPLETE，Issue 保持打开并继续 U2；U2 接收条件满足后才关闭。“确认关单结果”改为“更新 Issue 接收状态”，完成不再等价于所有关联 Issue CLOSED。

新增“PR 已合入、接受版本未保存”与“恢复结果冲突”场景。先保留原 delivery、Issue/PR 和内部实际 SHA，再核对合入证据；通过则补写接受游标并进入元数据，冲突则显示 × 与 `MERGE_RESULT_CONFLICT`，不重建或重新合入。

这两个场景依旧是合成状态；真实 Git、台账与恢复实现见 `packages/repo-sync/README.md`，与原型在同一分支和 PR 交付。内部平台先走 Git 路径，Issue/PR 创建与状态回读由人通过平台完成，工具登记映射并提供模板。

准备阶段的第一项写入操作是创建 / 复用内部 Issue，建立外部号到内部号的映射；之前先核对同步范围与基线。搬运阶段保留正确对应，内部 PR 引用内部编号。合入且代码核验后，确认的是同一个已映射 Issue 的状态：

| 情况 | 操作 |
| --- | --- |
| 接收条件全部满足，平台已经关闭 | 记录关单结果，复用对象 |
| 接收条件全部满足，内部仍打开 | 补充关闭正确映射的内部 Issue，记录结果 |
| 仍待后续交付 | 保存本笔接收记录，保持 Issue 打开；本笔完成后继续下一笔 |
| 普通关联，不具有关闭义务 | 保留现有状态，仅记录核对结果；已有关闭状态也不重新打开 |

关闭前必须核对来源 / 内部对象映射与本次代码核验记录；编号不匹配时阻止完成，展示 `ISSUE_MAPPING_UNVERIFIED`，不操作其他 Issue。关单失败只重试此环节，不重新建 Issue、搬运提交或合入 PR。结果保存到本笔交付，在开始下一笔后，历史详情与审计仍能说明是确认平台关单、程序补充关闭还是保留关联状态。可通过“待补充关单”和“普通关联 Issue”两个演示场景验证。

真实适配器需验证内部平台的自动关单能力及关闭关系；不能把所有关联 Issue 都视作应关闭，也不能直接沿用外部编号。GitHub 对默认分支的 PR 关闭关联和 commit 关闭关键词有明确规则；保留源提交消息时，其中的本仓 Issue 编号可能与内部不同，需要在真实平台专项验证，原型不证明自动关单兼容性。参考：[GitHub 官方说明](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)。

原型模拟具备平台适配器后的自动推进，主按钮明确写“继续演示”。当前 Git 版在内部平台对象环节需要人工操作与登记，Git 核验由程序执行，不声称读取了平台审批或关单状态。原型 PR 地址 `/internal/demo/core/pull/<id>?binding=<id>` 是本地模拟；Git 版使用操作者登记的具体 PR URL。

命令展示中的 Git 命令表示 Git 传输；Issue／PR 使用 `repo-sync` 适配器占位命令，明确未实现。标准 Git 本身不提供创建 Issue／PR 的接口。

内置交付 commit ID 为合成短 SHA；起始版本输入支持 7–40 位，版本卡简写显示前 8 位，悬停与复制保留完整 ID。首次独立快照接收在候选分支连接初始化历史，再合入目标上游版本；普通接收不重复连接。界面搬运阶段包含候选对象与内部分支推送，不表示直接推送上游 head 替换内部 main。

运行：`node packages/web/public/prototypes/repo-sync/server.mjs`，默认只绑定 127.0.0.1:5186。服务只提供原型文件与指定主题 CSS，不暴露整个仓库。

单元验证：本目录 `*.test.mjs`，用 `node --test` 执行；新增 `continuity.test.mjs` 验证共享 Issue 与恢复。
浏览器旅程：`browser-check.cjs`、`binding-browser-check.cjs`、`adoption-browser-check.cjs`、`delivery-browser-check.cjs`、`workbench-browser-check.cjs`、`progress-browser-check.cjs`、`continuity-browser-check.cjs`（均位于本目录，用 Node 执行）；使用可用 Playwright 和安装的 Chrome，产物落入系统临时目录。

声明边界：真实网络方向、Git 对象、平台审批与自动关闭需独立实现和验证；此原型证明 UI 状态与用户动作的因果，不证明生产同步能力。
